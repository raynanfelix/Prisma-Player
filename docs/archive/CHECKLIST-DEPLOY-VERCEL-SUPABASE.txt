 2. ABACATEPAY — WEBHOOK
--------------------------------------------------------------------------------
  2.1 Endpoint a cadastrar no painel da AbacatePay:
        POST  https://SEU-DOMINIO/api/webhooks/abacatepay

  2.2 Cadastre SEM o parâmetro ?webhookSecret= na URL (recomendado):
      O fluxo novo usa ABACATEPAY_WEBHOOK_SIGNING_SECRET como chave HMAC-SHA256
      que NUNCA viaja na URL. É a única chave aceita quando definida.

  2.3 Assinatura:
      - Verificação: HMAC-SHA256 do corpo cru, header
        x-webhook-signature (ou x-abacate-signature / x-signature).
      - Aceita hex, base64 e prefixo 'sha256='.
      - Teto de 500 chars na assinatura (BILLING.WEBHOOK_SIGNATURE_MAX_LENGTH).

  2.4 Eventos que o código processa:
        checkout.completed
        checkout.refunded
        checkout.disputed
        checkout.lost
        subscription.completed
        subscription.renewed
        subscription.cancelled
      Quaisquer outros eventos são ignorados com 200 {ok:true, ignored:true}.

  2.5 Em produção a assinatura HMAC é EXIGIDA por padrão (fail-closed), mesmo
      sem flags. Para garantir não-retrocesso, defina:
        ABACATEPAY_REQUIRE_HMAC=true
        ABACATEPAY_ALLOW_URL_SECRET=false
      (essas duas já matam o fallback legado de ?webhookSecret= na URL).

  Observação RM-01: antes qualquer fator autenticava (URL-secret OU assinatura).
  Agora a assinatura HMAC é a única via quando ABACATEPAY_WEBHOOK_SIGNING_SECRET
  está setada. Não volte o ?webhookSecret= de volta na URL do webhook.

        curl -I https://SEU-DOMINIO/robots.txt (deve existir, usa SITE_URL)

  5.2 Cron protegido:

             https://SEU-DOMINIO/api/cron     -> 200 (JSON com contadores)
        curl https://SEU-DOMINIO/api/cron     -> 401/503 (sem o segredo falha)

  5.3 Webhook AbacatePay:
        - Sem assinatura/secret  -> 401 invalid_webhook_signature
        - Com JSON inválido      -> 400
        - Evento não suportado   -> 200 {ok:true, ignored:true}
        - Testar fluxo real com devMode=true -> 200 {ok:true, ignored:true}
        - Testar checkout.completed pago (sem devMode) -> 200 {ok:true} e
          linhas em subscriptions + payment_webhook_events processadas.

  5.4 Embed:
        - /api/embed/:id e /api/embed/:id/manifest respondem 200 com token.
        - Sem EMBED_ORIGIN_SECRET configurada -> 403 invalid_origin_token.
        - Encher o rate limit até os máximos configurados e ver 429.

  5.5 Billing / créditos IA (RH-01):
        - Comprar créditos IA -> verifica ai_credit_ledger com lançamento
          'ai-credit:<checkout_id>'.
        - Estornar via AbacatePay (checkout.refunded) -> revoke_ai_credit_purchase
          reverte a entrega, wallet nunca negativa, registro 'refunded'.
        - Reenviar o mesmo evento (duplicado) -> processa uma vez (idempotente).

  5.6 Quota de storage (RM-04):
        - Tentar criar vídeo com status='failed' via cliente não-admin deve
          ser bloqueado com forbidden_status_transition.
        - O cálculo de cota soma também os videos 'failed'.

--------------------------------------------------------------------------------
 6. LIMITAÇÃO CONHECIDA (risco residual documentado na revisão)
--------------------------------------------------------------------------------
  O fluxo de conversão cross-site (trackConversion no player-loader + fetch
  cross-site para a API) depende de cookie de terceiros (pp_embed, SameSite=None
  em iframe). Navegadores que bloqueiam cookies de terceiros (Safari ITP,
  Firefox ETP strict, Chrome pós-phaseout de 3PC) perdem a conversão e, por
  consequência, deliverServerPurchase/webhook de conversão não disparam. É
  comportamento esperado até uma estratégia de fallback sem cookies (ex: token
  no postMessage) ser implementada.
